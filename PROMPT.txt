## 1. Viewer must be logged in for files owned by a logged-in user

Confirmed scope: **every** file in `user_file_uploads` (i.e. any file
with a non-null `owner_id`) requires the viewer to also be authenticated
— not just files that are also password-protected. This applies
regardless of whether `is_password_protected` is true or false.

Anonymous uploads (`anonymous_file_uploads`) are unaffected — they stay
publicly viewable with no login requirement, matching current behavior.

Implementation: on the `GET /f/{file_id}` route (or wherever that view
is actually served — locate the real route first), after looking up
which table the file_id belongs to:
- If it resolves to `anonymous_file_uploads` → serve normally, no auth
  check.
- If it resolves to `user_file_uploads` → require
  `request.state.user_id` to be present (same middleware pattern already
  used elsewhere — `core/auth_middleware.py`). If absent, redirect to
  `/login?next=/f/{file_id}` so the viewer lands back on the file after
  logging in, using the same `next` param pattern already used for
  signup/login elsewhere in the app. Do not require the viewer to be the
  *owner* — any authenticated user, not just the uploader, satisfies
  this check.

## 2. Password lockout: 3 attempts, 5-minute lock — intentionally different from snippets

The live snippet lockout (`db/access_control.py`,
`increment_failed_attempt`) actually locks for **10 minutes** after 3
failed attempts — the original planning doc said 5 minutes, but the real
implemented code is 10. Files should use **5 minutes**, not 10. This is
a deliberate difference from snippets, not a bug to "fix" back to match
— do not copy the 10-minute value from `access_control.py` when writing
the file equivalent.

Implementation: mirror `db/access_control.py`'s structure
(`get_or_create_access`, `increment_failed_attempt`, `mark_success`) in
whatever file already handles `file_access_control` reads/writes, but
with the lock interval set to `INTERVAL '5 minutes'` instead of `'10
minutes'`. Confirm the actual file service already has these functions
partially built before adding — reuse rather than duplicate if a partial
version exists.

Recall: `file_access_control.file_id` references `user_file_uploads(id)`
only — anonymous files have no row in this table and can't be locked,
so this logic only ever applies to logged-in-owned files (which, per
§1, already require the viewer to be logged in before even reaching a
password prompt).

## 3. Toast/message box width — sizing to content, not a fixed width

Symptom: short message text, but the box renders far wider than the
text needs, leaving a large empty gap after the text. This is the
classic signature of the box's width coming from something other than
its own content — most likely one of:
- A fixed `width` (or `min-width`) left over from sizing against a
  longer message that used to be the only one shown
- The toast being a flex/grid child that's stretching to fill its
  parent's available width (e.g. `align-self: stretch` inherited, or a
  parent using `justify-content: stretch` instead of `flex-end`)
- `width: 100%` somewhere in the chain instead of `width: fit-content` /
  `width: max-content`

Fix: the toast box should size to its own content
(`width: fit-content` or `width: max-content` on the box itself, with no
competing fixed width elsewhere in its CSS chain), while its
*positioning* (bottom-right of the viewport) stays exactly as-is — only
the width calculation is the problem, not the placement.

Locate the actual toast component's CSS before patching — there may be
more than one message type sharing this component ("Copied!", and
whatever others are being shown), so confirm the fix applies at the
shared component level rather than needing to be repeated per message
type.
