Review the current **Remote API Proxying Mode implementation plan** and revise it before implementing anything.

For now, focus **ONLY on these four points**. Do not expand the scope into other proxy concerns yet.

### 1. Use an explicit remote-proxy mode

Do **not** use the absence of `DB_URL` as the condition for enabling remote proxying.

The current proposal says:

> "Add a proxy handler for API endpoints when running without a local `DB_URL`."

Change this design to use an explicit configuration flag, for example:

```env
REMOTE_API_MODE=true
LIVE_API_URL=https://codealive.onrender.com
```

The behavior should be:

* `REMOTE_API_MODE=true` → local FastAPI serves the frontend but proxies backend/API operations to `LIVE_API_URL`.
* `REMOTE_API_MODE=false` or unset → normal local backend behavior.
* Missing `DB_URL` alone must **never automatically imply remote mode**.

Also make sure that when remote mode is enabled, local database initialization is skipped so the temporary frontend developer can run the UI without having any database credentials or local backend environment secrets.

### 2. Do not proxy arbitrary routes

Do not implement a generic "proxy anything that isn't a frontend route" mechanism.

Create an explicit allowlist of the backend routes that are supposed to be proxied.

For example, depending on the actual CodeAlive routes:

```text
/api/*
/save
/waitlist
```

But **inspect the existing CodeAlive codebase first and determine the actual backend/API routes that need to work in remote mode**.

Do not blindly proxy:

```text
/*
```

or every unknown/unmatched route.

The goal is:

```text
Local FastAPI
├── Frontend HTML/CSS/JS → serve locally
├── Explicitly allowed API routes → proxy remotely
└── Everything else → retain normal local routing behavior
```

### 3. Authentication and cookies — investigate before implementing

Do not assume that simply forwarding:

```text
Cookie
Authorization
```

will make authentication work correctly.

First inspect the existing CodeAlive authentication implementation and determine:

* Whether authentication uses cookies, JWTs, or both.
* Where the authentication cookie is created.
* Its `Domain`, `Path`, `Secure`, `SameSite`, and `HttpOnly` attributes.
* How authenticated API requests currently identify the user.
* Whether login is expected to happen through the deployed backend.

Then determine exactly what happens in this architecture:

```text
Browser
   ↓
localhost:8000
   ↓
Local proxy
   ↓
https://codealive.onrender.com
```

Specifically verify whether the deployed backend's authentication cookie can correctly work through the local proxy.

If cookie rewriting or another mechanism is required, include it in the revised plan.

**Do not implement authentication handling based on assumptions. Inspect the existing code first and report what needs to happen.**
